这一篇是我准备了两天的。
事情起因是这样的——前几天我在 GitHub 上闲逛，看看英文社区有没有什么跟学术写作相关的新项目。**我之前自己写过几套 Claude Skill 用在科研里**，文献综述闭环、降 AI 率、引用核查——前面几篇文章里都写过。一直以为我做的这些算是"国内学术圈的 AI 工具实验先锋"。
然后我看到了一个叫 **academic-research-skills** 的 repo。
第一眼让我愣住的是星标数——**26,500 stars，2,200 forks**。这个量级在 GitHub 整个生态里都算热门项目，更何况是一个看名字像"小众学术工具"的 repo。
第二眼让我愣住的是更新时间——**最新版本 v3.10.0 发布于 2026 年 6 月 1 日，也就是前天**。这不是个三年前留下来的老项目，是个**活跃迭代到至今的成熟工具**。
我读完 README 第一遍的时候，泡了杯茶。然后从头读了第二遍。然后第三遍。
这一篇是我读完三遍之后想跟你说的话。
***
# 一、26.5k 星的项目到底装了什么
academic-research-skills 不是一个 Skill，是**五个 Skill 串起来的完整研究流程**。
第一个叫 **Deep Research**。它的内部是一个 13 个 agent 组成的研究团队，对应 7 种工作模式——完整研究、快速调研、批判性 review、文献综述、事实核查、苏格拉底引导对话、PRISMA 系统综述。我读到 "PRISMA systematic review support with risk-of-bias assessment" 那一句的时候停了一会儿——**PRISMA 是医学和社科系统综述的金标准协议，写过 SCI 系统综述的人都知道它有多严格**。把 PRISMA 嵌进一个 Claude Skill 里，意味着这个开发者非常严肃地在对待学术规范。
第二个叫 **Academic Paper**。12 个 agent 组成的写作 pipeline，对应 10 种模式——完整写作、规划、只出 outline、修订、修订指导、只写摘要、文献综述、格式转换、引用核查、AI 使用披露。输出格式覆盖 Markdown、DOCX (通过 Pandoc)、LaTeX、PDF (APA 7.0 / Chicago / IEEE 三套引用规范)。这里最让我注意的是 "Style calibration learning from user's prior work"——**它能学习用户自己以前的写作风格做风格校准**。这不是简单的"AI 生成论文"，是"AI 模仿你自己的语调帮你完成下一篇论文"。
第三个叫 **Academic Paper Reviewer**。7 个 agent 做多视角审稿，每个维度按 0-100 评分。提供 5 种 review 模式，外加可选的 calibration——你给它一份你认为是"金标准"的审稿意见，它学着像那个标准去审。
但是这一块里有一个细节我读到第三遍才完全理解——它内置了一个 **Devil's Advocate**（魔鬼代言人）角色，**带 concession-threshold protocol，防止 premature agreement**。我后面单独花一节讲这个。
第四个叫 **Academic Pipeline**。这是整套系统的总调度器，**10-stage orchestrator**，把"研究 → 写作 → 审稿 → 修订 → 定稿"五大流程串成一条流水线。**关键设计是 Stage 2.5 和 Stage 4.5 两个 mandatory integrity gates**——也就是流水线在第 2 步半和第 4 步半各有一道强制完整性闸门，如果检查不过，整个 pipeline 拒绝输出。这两道闸门用一份 7 模式 AI 故障检查清单——这件事我后面也单独讲。
第五个叫 **Material Passport**，schema 9+ 版本。它是这套系统的"记忆载体"——你今天写一半合上电脑，明天打开继续，它能从上次断点续起。底层是个 append-only ledger（只追加日志），所有的中间产物、决策依据、引用来源都被记录下来，便于追溯。
读完这五个 Skill 的结构，我心里出现了一个画面——**这不是一个"AI 帮你写论文"的工具，这是一个"AI 与你共同管理整个研究项目"的基础设施**。

# 二、那个让我停下来的设计原则——"Copilot, not pilot"
academic-research-skills 在它的设计原则里反复强调一句话：
> The project frames AI as "copilot, not pilot."

副驾驶，不是司机。
这句话表面看是个口号，但它在代码里是**实实在在的硬约束**。整个 pipeline 在每一个关键节点都要求**用户显式确认**才能继续——这意味着你不能像用 ChatGPT 那样"丢个任务让它跑十分钟自己出结果"。**你必须在过程中持续介入，做决定**。
我读到这里的时候，第一个感觉是——**这个台湾华人开发者，独立得出了我在 013 / 014 / 015 那几篇里反复强调的"闭环原则"**。
更让我有点不甘心的是——**他比我做得更系统**。
我那几篇文章里立的"闭环铁律"是文字层面的承诺——研究者你要做这件事、不要做那件事。但是 academic-research-skills 把这些承诺**嵌进了代码层面的强制约束**。Stage 2.5 完整性闸门、Devil's Advocate 强制对立审视、Semantic Scholar API 自动引用核查——这些不是建议，是**绕不过去的关卡**。
我看到 README 里有一句话特别让我警醒：
> the pipeline refuses output when HIGH-WARN violations surface (fabricated references, unsupported claims, constraint violations).

翻成人话：**如果检测到伪造引用、缺乏证据支撑的断言、或者违反约束的输出——这个 pipeline 直接拒绝出结果**。
这句话拿到我们 013 那篇讲的 Nature 30-55% AI 编造引用问题面前——**它就是工程化的答案**。你不需要研究者自觉去核查每一条引用了，工具会替你拦截。
这是把闭环原则从"道德要求"变成"系统约束"。**这一步差距，是我自己写的 skill 跟它最大的距离**。

# 三、Devil's Advocate 和 concession-threshold——一个我没想到的设计
接下来这一节我得仔细讲，因为它解决的是我一直没想清楚的一个问题。
我们用 AI 写论文 / 改论文 / 跟 AI 讨论研究问题的时候，**最大的隐性陷阱不是 AI 编数据，是 AI 太顺着你**。
你说"我觉得 X 方法比 Y 方法好"——AI 大概率会先肯定你的观点，然后给你补充几条支持理由。**它很少真正站到对立面跟你硬刚**。这种现象在 AI alignment 圈有个专门的词叫 sycophancy（阿谀奉承）——大模型为了用户满意度倾向于赞同用户。
后果是什么？**研究者在跟 AI 讨论的过程中，慢慢失去了"被质疑"的能力训练**。
你以前在组里讲一个 idea，资深的师兄师姐会当面挑你毛病。现在你跟 AI 讨论同样的 idea，它给你点头。**你的思考没有被真正压力测试过，但你已经感觉自己想清楚了**。
这是个非常隐蔽的问题。
academic-research-skills 里的 Devil's Advocate agent 是专门干这个的——**它的工作就是反对你**，找你论证中的漏洞，提出反例和反证。
但它做了一个更细的设计，叫 **concession-threshold protocol**——**让步阈值协议**。
意思是：Devil's Advocate 不能因为你反驳了一句"但是我有数据"就让步同意。它有一个内置阈值——你必须提供多强的证据、多详尽的论证才能让它"退让"一步。**这个阈值的存在防止了 AI 在受到任何压力时就软化立场**。
我读到这个设计的时候，给我组里的博士师弟发了一条微信——"以后你写论文的初稿先让 AI 当 Devil's Advocate 跟你辩 30 分钟，再交给我看。"
师弟回了一个问号。
我没解释。但这件事我想了很久——**学术训练的核心不是"得到答案"，是"经历被挑战的过程"**。Devil's Advocate + concession-threshold 把"被挑战"这件事，从"靠运气遇到一个好导师"变成"工具可以提供的服务"。
这件事的长远意义可能比我们现在以为的大。

# 四、Semantic Scholar API 交叉核查——硬通货的引用核查
接下来这一节短一点，但它呼应的是我那篇五步核查实战法。
academic-research-skills 在 anti-leakage protocols 里嵌入了 Semantic Scholar API 调用——**每一条 AI 生成的引用都会被自动跟 Semantic Scholar 的真实文献库交叉验证**。
我那篇文章里讲的"五步法"是教研究者人工核查。**这个 repo 把第五步——多库交叉验证——自动化了**。
这件事的工程意义远远超过它表面的功能价值。**它意味着引用真实性这件事，可以变成一个"事前防御"而不是"事后核查"的环节**。
研究者不需要每写完一段都去 Crossref 查一遍 DOI——pipeline 在生成引用的同时已经验证过了。如果某条引用在 Semantic Scholar 找不到，pipeline 直接标红或拒绝输出。
我自己写的 skill 走到第 7 个（引用核查）的时候，是依赖研究者人工核对的。**这个 repo 不依赖研究者，它依赖 API**。这是个更稳健的设计。
我承认我有点羡慕。

# 五、这件事对中文科研工具圈意味着什么
写到这里我想停下来说一段更大的画面的话。
国内中文学术圈这两年关于"AI 用于论文写作"的公众号文章，**数量大概是英文社区的十倍**。光是我自己关注的同行账号，每周都能看到三五篇"用 GPT 写论文的 X 个方法"、"Claude 帮你做综述的 Y 个提示词"。
但**中文圈贡献出来的开源工具，几乎为零**。
我们在写"how to" 文章，国外在写"工具本身"。
academic-research-skills 这种规模和质量的开源项目，**在中文 GitHub 社区你找不到对标**。Cheng-I Wu 个人开发到 26.5k 星，相当于一个独立开发者把整套 PhD pipeline 工程化贡献给社区。这件事在英文学术工具圈不是孤例——Anthropic 上个月推出了 Claude for Life Sciences；OpenAI 上月也把 Codex 做 PPT 列为官方 use case；各大研究机构内部都在写自己的 "research skills"。
**英文圈正在从"个人摸索 AI 工具"过渡到"基础设施化 AI 工作流"**。
中文圈呢？我们还停留在第一阶段。每个研究者各自写自己的 prompt 库、各自摸索自己的工作流、各自重复发明轮子。**没有一个有标杆性的、可装即用的、开源持续维护的中文学术工具**。
我作为一个不算资深的高校副教授，写这一段是有些惭愧的。**我这两年发了那么多公众号文章讲"怎么用 AI"，但我没有贡献过一行可复用的代码**。
这不是单个人的问题——是中文学术工具生态的整体问题。我们太擅长写"how to"，太不擅长做"基础设施"。

# 六、我会推荐学生用这个吗——我的真实纠结
写到这里就该收一收了。但我得诚实——**我对要不要让我组里的学生用这个，还在纠结**。
支持的理由很明确：
工具上确实先进。它解决的问题对博士生来说是真问题。如果我组里的博三、博四学生用它管理自己的研究 pipeline，至少能省下 30% 的"管理成本"（找资料的时间、记笔记的时间、改稿子的时间），把节省下来的时间用在真正的思考上。
但我犹豫的部分是——**我不确定它对博一、博二的学生是好事**。
学术训练最关键的不是"得到一篇论文"，是"经历完整的研究过程"。你必须读完那 30 篇文献才能感受到"原来这个领域真正的争议在哪儿"。你必须自己改三轮 Introduction 才能体会到"为什么开篇这一段必须重写"。**这些痛苦的过程是不能跳过的——它们就是博士训练本身**。
如果你把这个 26.5k 星的 pipeline 直接给博一学生用，**他可能会得到一份看起来不错的论文初稿，但他没有经历过把 30 篇文献读到滚瓜烂熟的过程**。这件事的长期代价可能是——**他到博三的时候，仍然不知道自己领域的真正问题在哪里**。
这不是工具的错。是教育的问题。
我目前的折中想法是——博一、博二学生**不让用**这种 pipeline 型工具，只能用单独的 Skill (比如引用核查、AI 率诊断)。博三以后**让他们装这个 repo**，让 pipeline 帮他们管理"已经掌握了的工作流"，但不替他们做"还没学会的思考"。
我不知道这个折中对不对。可能五年后回头看会觉得太保守，也可能会觉得太激进。
这就是我的真实状态——**对这种规模和成熟度的工具，我心里其实充满了不确定**。
